# Forge Artifacts: current-system audit

Audit date: 2026-07-13

Scope: current Forge code in the isolated `codex/artifacts-system-audit` worktree. This is a static product, UX, security, data-model, API, rendering, navigation, and test audit. No application code was changed. The report does not claim visual or accessibility conformance: no authenticated live flow or browser screenshots were available to this worker, so visible behavior is inferred from the implemented JSX and API contracts and should be confirmed in browser QA.

## Executive verdict

Forge has a useful v1 foundation: a workspace-scoped artifact head, append-only body revisions, stable slugs, source promotion, archive/restore, MCP tools, shared Markdown rendering, artifact embeds, and a polymorphic attachment backend. The strongest existing pieces are the shared rich-content renderer and the fact that artifacts already participate in agent context, Canvas, Command Center, and the audit stream.

It is not yet a trustworthy publishing or collaboration system. The largest blockers are authorization gaps for narrowed API keys, a server-side URL-fetch path that is vulnerable to SSRF, revision semantics that do not actually separate draft from published content, and the complete absence of artifact-level sharing/access controls. The UI exposes only a thin Markdown textarea and a non-interactive history list; attachment support exists behind the API but is not available on artifact pages. Search is local to the first fetched page, linked artifacts are not surfaced on their owning issue/project, and archived artifacts remain directly readable.

Before adding interactive/site-style rendering, Forge should harden the authority and revision foundations. Rich rendering increases the consequence of ambiguous publishing, weak ACLs, and unsafe external content.

## What exists today

- **Durable head plus revisions.** `Artifact` stores the current title/body/status/slug and points at an `ArtifactVersion`; `ArtifactVersion` stores numbered snapshots with changelog and actor IDs (`prisma/schema.prisma:2910-2999`). Migration `0032` created the two-table shape and indexes (`prisma/migrations/0032_artifact_primitive/migration.sql:39-141`).
- **Artifact categories and lifecycle labels.** The Prisma enum includes document, decision, runbook, report, spec, brief, verification, and note; lifecycle labels are draft, in review, accepted, and archived (`prisma/schema.prisma:469-497`).
- **Create, edit, promote, archive, restore, duplicate, and hard delete.** The tRPC router exposes the lifecycle and a source promotion path for chat messages, comments, notes, agent runs, and issues (`src/server/routers/artifact.ts:59-509`).
- **Automatic body snapshots.** Creation seeds version 1; body changes normally append a version and update `currentVersionId` (`src/server/services/artifact-service.ts:120-187`, `src/server/services/artifact-service.ts:210-295`).
- **Authenticated list and detail pages.** Artifacts are reachable from the Planning sidebar and `g f` chord (`src/components/sidebar-nav.ts:65-77`). The index has active/archived tabs, type chips, a search input, and card actions (`src/app/(app)/w/[slug]/artifacts/page.tsx:63-334`). The detail view renders Markdown, edits in a textarea, exposes type/status selectors, and shows revision metadata (`src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:31-297`).
- **Shared rich renderer.** Artifact bodies receive headings, emphasis, fenced code, quotes, task/ordered lists, tables, structured `:::data` blocks, artifact embeds, issue refs, agent mentions, attachment tokens, direct media, and selected provider embeds (`src/components/markdown/attachment-renderer.tsx:37-68`, `src/components/markdown/attachment-renderer.tsx:431-653`, `src/components/markdown/attachment-renderer.tsx:836-1067`). Known standalone URL providers are YouTube, GitHub, Loom, and one additional design-provider embed; unknown links fall back to ordinary links (`src/components/embeds/embed-detector.ts:1-9`, `src/components/embeds/embed-detector.ts:50-132`).
- **Artifact-in-Markdown embeds.** `:::artifact <id>` resolves a compact workspace-scoped payload and renders Markdown, a whole-document code fence, or an image-shaped body in a bounded card (`src/server/routers/artifact.ts:134-201`, `src/components/embeds/artifact-embed.tsx:25-40`, `src/components/embeds/artifact-embed.tsx:73-133`).
- **Polymorphic file/link storage.** Attachment targets include `artifact`; file types cover images, PDF, text/Markdown/HTML/data formats, office documents, media, and ZIP up to 25 MiB (`src/server/services/storage.ts:35-97`). The shared lightbox can preview images, PDFs, sandboxed HTML/links, video, audio, and text (`src/components/attachments/attachment-lightbox.tsx:464-503`, `src/components/attachments/attachment-lightbox.tsx:506-620`).
- **Agent and orchestration integration.** MCP supports list/get/create/update/archive/promote; agent completion can return produced artifact IDs; entity hydration supplies artifact content to Canvas/context sets (`src/server/services/mcp.ts:8264-8535`, `src/server/services/entity-hydration.ts:408-451`). Command Center shows six recent artifacts (`src/server/routers/command-center.ts:143-155`, `src/app/(app)/w/[slug]/command-center/page.tsx:457-479`).
- **Basic lifecycle tests.** Integration tests cover create, slug collisions, body snapshots, archive/list, promotion, issue linking, restore, duplicate, delete, cross-workspace restore, and the admin delete gate (`src/server/routers/__tests__/artifact.test.ts:35-169`, `src/server/routers/__tests__/artifact-lifecycle.test.ts:33-195`). Shared-renderer tests cover URL scheme safety and selected rich previews (`tests/unit/markdown-url-safety.test.ts:12-50`, `tests/unit/rich-rendering.test.ts:40-162`).

## Findings ordered by severity and opportunity

### Critical — security and authorization

- **[C1] Narrowed API keys can read artifacts outside their permitted project/initiative/label lane.** The `artifacts.list` and `artifacts.get` MCP handlers require only `READ_ISSUES`; neither applies `buildKeyScopeWhere` nor calls `assertKeyScope` (`src/server/services/mcp.ts:8273-8355`). This means a key narrowed to one project can list and fetch every artifact in the workspace, including artifacts linked to issues outside that key's scope. This contradicts the narrowing contract implemented in `assertKeyScope` (`src/server/services/api-key-auth.ts:84-154`). **Intent:** make artifacts a first-class scope target or derive scope from `issueId`/`projectId`; deny unanchored artifacts to narrowed keys unless a separate workspace-artifact grant exists.
- **[C2] Narrowed API keys can also mutate artifacts outside their lane when the artifact has no `issueId`.** Create checks only `issueId`, ignoring `projectId`; update/archive check scope only when the fetched artifact has an `issueId` (`src/server/services/mcp.ts:8389-8408`, `src/server/services/mcp.ts:8439-8460`, `src/server/services/mcp.ts:8468-8482`). The execution-target resolver likewise returns `none` for standalone artifacts and ignores a project-only anchor (`src/server/services/mcp-exec.ts:163-186`). **Intent:** centralize artifact authorization and call it from every read/write path; include project and initiative derivation and explicit policy for standalone artifacts.
- **[C3] Link-title enrichment permits server-side requests to internal network targets.** `isSafeExternalUrl` checks only `http:`/`https:` (`src/lib/url-safety.ts:8-26`). `attachment.attachLink` then fetches the supplied URL for metadata (`src/server/routers/attachment.ts:181-203`), and `fetchLinkMetadata` follows redirects without DNS/IP allow/deny checks (`src/server/services/storage.ts:801-867`). Artifact is an allowed attachment target, so a workspace member or agent can make the Forge server request loopback, link-local/cloud metadata, or private-network endpoints. **Intent:** resolve and reject private/reserved IP ranges on every redirect hop, disable automatic redirects or revalidate each hop, cap response headers/body, and test DNS rebinding/IPv4/IPv6 forms. Until hardened, do not fetch metadata for arbitrary URLs.

### High — publication integrity, access, and data lifecycle

- **[H1] “Published version” is not a real product state.** Schema comments say `body` and `currentVersionId` represent canonical published content (`prisma/schema.prisma:2914-2917`, `prisma/schema.prisma:2932-2946`), but every ordinary body save on a DRAFT appends a version and moves `currentVersionId` (`src/server/services/artifact-service.ts:236-267`). `publish: false` still updates the head body without moving the version pointer, and every reader renders the head `body`, not the pointed revision (`src/server/routers/artifact.ts:38-57`, `src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:202-203`). **Intent:** separate editable draft head from immutable revisions and publication pointers (`latestRevisionId`, `publishedRevisionId`), make publish an explicit operation, and render the correct revision per surface.
- **[H2] Metadata changes are silently outside revision history.** Title, summary, type, and status edits mutate the head in place and do not create a version (`src/server/services/artifact-service.ts:205-209`, `src/server/services/artifact-service.ts:258-267`); tests explicitly lock in this behavior (`src/server/routers/__tests__/artifact.test.ts:89-98`). Old version rows therefore do not reliably reconstruct what viewers saw, and an “accepted” artifact can be retitled/retyped without a new revision. **Intent:** version all share-visible content/metadata, or maintain a separate immutable change history that can reconstruct each published state.
- **[H3] Concurrent edits can be lost or fail unpredictably.** `updateArtifact` reads the head and computes `nextVersion` before entering the write transaction (`src/server/services/artifact-service.ts:214-239`). There is no revision precondition, optimistic-lock field, or editor conflict UI; simultaneous saves can overwrite the head and race on the unique `(artifactId, version)` index (`prisma/schema.prisma:2997-2998`). **Intent:** require `baseRevisionId`/`updatedAt`, allocate revisions transactionally with retry, surface a compare-and-merge conflict flow, and preserve both attempted bodies.
- **[H4] The history UI is a log label, not usable versioning.** The detail page fetches only the latest 20 version headers and renders version number/date/changelog (`src/server/routers/artifact.ts:102-127`, `src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:63-66`, `src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:250-273`). Users cannot open a historical body, compare, restore-as-new, identify the author, copy a version link, or download/export it. `listVersions` returns bodies but is unused by this page and has no cursor (`src/server/routers/artifact.ts:217-251`). **Intent:** add a revision drawer with preview, author, changelog, diff, compare, restore-as-new-revision, immutable version URL, and pagination.
- **[H5] There is no artifact-level sharing or access-control model.** `Artifact` has creator fields but no owner role, visibility, grants, public token, public slug, or published audience (`prisma/schema.prisma:2923-2969`). Every artifact page lives under the authenticated app layout (`src/app/(app)/layout.tsx:16-24`), and all artifact read/write procedures use `workspaceProcedure`, which checks membership but not role (`src/server/trpc.ts:94-121`, `src/server/routers/artifact.ts:59-325`). Consequently every workspace role, including GUEST, can create, edit, change status, archive, restore, and duplicate any artifact; only hard delete is admin-gated (`src/server/routers/artifact.ts:419-447`). **Intent:** model audience (`private`, named principals, workspace, public-link) separately from role (`viewer`, `commenter`, `editor`, `owner`); gate every route/mutation through one authorization service; make public sharing admin-policy controlled and off by default.
- **[H6] “Accepted” has no approval or immutability semantics.** Any workspace member can set any `ArtifactStatus` directly through a select or mutation (`src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:226-241`, `src/server/routers/artifact.ts:284-313`). There is no state-transition validation, reviewer, review gate, acceptance timestamp, or rule preventing edits to accepted content. **Intent:** define lifecycle transitions, reviewers/approvals, permission gates, acceptance metadata, and whether editing an accepted artifact creates a new draft while the accepted publication remains stable.
- **[H7] Archive state is inconsistent and does not revoke direct access.** Archive writes both `archivedAt` and `status=ARCHIVED` (`src/server/services/artifact-service.ts:303-343`), but create/update also accept `status=ARCHIVED` without setting `archivedAt` (`src/server/routers/artifact.ts:253-313`). Conversely, `get`, `getBySlug`, and `getForRender` do not filter `archivedAt`, so an archived artifact remains readable by direct URL and embeddable (`src/server/routers/artifact.ts:102-215`). Restore always changes an archived status to DRAFT rather than the prior status (`src/server/routers/artifact.ts:327-367`). **Intent:** use one canonical lifecycle representation; distinguish archive from unpublish/revoke; make archived-read behavior explicit; persist and restore prior publication state only when intended.
- **[H8] Hard delete can orphan attachment rows and object-storage bytes.** Attachments reference artifacts through untyped `targetType`/`targetId` with no artifact foreign key (`prisma/schema.prisma:1424-1460`). Artifact hard delete removes versions and the artifact but neither deletes artifact attachments nor their S3 objects (`src/server/routers/artifact.ts:449-476`). Those rows become unresolvable through ordinary target validation and continue consuming quota/storage. **Intent:** transactional/queued purge of every dependent reference and object; show an impact count before deletion; keep a durable purge audit record.
- **[H9] Artifact attachment activity is not audited.** Upload finalization, link attachment, and attachment deletion emit `recordChange` only when `targetType === "issue"` (`src/server/routers/attachment.ts:123-170`, `src/server/routers/attachment.ts:181-249`, `src/server/routers/attachment.ts:315-365`). This contradicts the documented promise that agentic primitives write audit/activity events (`docs/concepts/primitives.md:265-285`). **Intent:** emit target-appropriate audit/activity for artifact file/link add, remove, replace, and public-access changes.
- **[H10] The backend supports artifact files/links, but the artifact product does not.** `artifact` is a valid target (`src/server/services/storage.ts:83-97`), yet the only upload/list UI is hard-coded as `IssueAttachmentsPanel({ issueId })` with `targetType: "issue"` throughout (`src/components/attachments/issue-attachments-panel.tsx:47-60`, `src/components/attachments/issue-attachments-panel.tsx:115-213`). Neither artifact page mounts an attachment manager. Users cannot upload an image/file, attach a link, insert its Markdown token, browse assets, or remove it while authoring an artifact. This also leaves the original Wave 2 acceptance item “reusable AttachmentsPanel target abstraction” incomplete (`docs/audits/2026-05-19-forge-agentic-work-os-execution-plan.md:250-264`). **Intent:** extract a target-agnostic asset panel/editor integration, with upload/paste/drop, insertion at cursor, gallery, alt text, replace, asset reuse, and permission-aware deletion.

### Medium — usability, rendering, discovery, and maintainability

- **[M1] Artifact search is a client-side filter over only the first page.** The page calls `artifact.list` with default limit 50, never follows `nextCursor`, and filters only loaded title/summary in memory (`src/app/(app)/w/[slug]/artifacts/page.tsx:67-106`). The router has no search input and returns full `body` for every list row because `artifactSelect` includes it (`src/server/routers/artifact.ts:38-57`, `src/server/routers/artifact.ts:59-100`), creating a worst case of roughly 10 MB of body text before transport overhead. **Intent:** server-side indexed search across title, summary, body, type, status, author, source, and linked work; slim list projections; stable cursor pagination; saved filters and sort.
- **[M2] Global navigation cannot find artifacts.** The command palette describes and queries issues, projects, initiatives, saved views, sprints, agents, goals, crews, and plans, but has no artifact bucket (`src/server/routers/command-palette.ts:5-24`, `src/server/routers/command-palette.ts:33-108`, `src/server/routers/command-palette.ts:129-328`). Artifacts are reachable from sidebar/Command Center only if the user already knows where to look. **Intent:** add artifact results, direct slug/version matches, recent/favorite artifacts, and keyboard actions.
- **[M3] Linked work does not become navigational context.** The data/API can associate an artifact with an issue or project (`prisma/schema.prisma:2947-2968`, `src/server/routers/artifact.ts:61-100`), but the artifact index does not offer issue/project filters, and artifact detail does not show or link its issue/project. The list page calls only active/archived variants (`src/app/(app)/w/[slug]/artifacts/page.tsx:67-71`). **Intent:** show artifacts on issue/project pages; show backlinks and related work on artifacts; add filters, relationship editing, and “used in” references.
- **[M4] Provenance exists as IDs but is not a usable backlink.** Promotion stores `sourceType`/`sourceId` (`src/server/services/artifact-service.ts:362-398`), while detail renders only “Promoted from {type}” text with no source title, location, author, quote, or link (`src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:243-247`). Polymorphic IDs have no database FK and can silently dangle (`prisma/schema.prisma:2939-2943`). **Intent:** typed provenance records, hydrated clickable backlinks, source snapshots, broken-source states, and chain-of-custody metadata per revision.
- **[M5] Promotion is exposed only on agent chat messages.** The reusable button and service support five source types (`src/components/capture/promote-to-artifact-button.tsx:9-19`, `src/server/services/artifact-service.ts:355-377`), but the only mounted affordance is on persisted non-user chat messages (`src/components/mission-control/chat-message.tsx:350-368`). **Intent:** add promote/capture actions to comments, notes, run summaries, issue descriptions, attachments, and selected text; offer title/type/summary/relationship review before creation.
- **[M6] Creation and editing are too thin for a durable artifact.** Index creation asks only for a title and creates an empty default document (`src/app/(app)/w/[slug]/artifacts/page.tsx:337-375`). Quick Create similarly creates a title plus normally empty body (`src/components/quick-create.tsx:888-900`). Detail editing is a raw, minimum-480px textarea plus optional changelog, with no preview split, formatting toolbar, templates, autosave, dirty-state warning, cancel/revert, asset browser, or conflict state (`src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:168-203`). **Intent:** template-aware composer, source/render split or rich editor, autosaved drafts, explicit publish, keyboard formatting, preview, revision note, cancellation, and recovery.
- **[M7] Rendering is rich Markdown, not a typed artifact runtime.** Artifact type influences labels but not the detail renderer; all bodies go through the same Markdown component (`src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:202-203`). `getForRender` infers image/code only when the entire body matches a narrow regex (`src/server/routers/artifact.ts:166-200`). There is no declared content format, renderer version, sandbox/runtime class, asset manifest, dimensions, or export format. **Intent:** renderer registry with explicit `contentKind`/schema: Markdown, code, image/gallery, SVG, diagram, data/chart, sandboxed HTML, interactive local bundle, and separately governed hosted site/app.
- **[M8] External Markdown image handling is internally inconsistent.** `getForRender` classifies a body containing `![alt](https://...)` as an image (`src/server/routers/artifact.ts:166-183`), but the inline renderer recognizes image syntax only for `forge-attachment:` IDs (`src/components/markdown/attachment-renderer.tsx:74-99`, `src/components/markdown/attachment-renderer.tsx:105-128`). The “image” artifact branch hands the same body back to that renderer (`src/components/embeds/artifact-embed.tsx:110-117`), so an external Markdown image becomes punctuation plus a link rather than an image. **Intent:** one normalized image block model, with safe proxying, explicit external-image policy, dimensions, loading/error states, alt-text validation, and gallery/lightbox behavior.
- **[M9] Link previews are provider-specific or bare, not general link cards.** Standalone URLs are promoted only when they look like direct media or match the small provider detector (`src/components/markdown/attachment-renderer.tsx:500-519`, `src/components/embeds/embed-detector.ts:1-9`). `forge-link` renders a compact favicon/title chip only (`src/components/markdown/attachment-renderer.tsx:1396-1410`), and link attachments open a sandboxed iframe that many sites will refuse (`src/components/attachments/attachment-lightbox.tsx:506-559`). **Intent:** a sanitized cached Open Graph card (title, description, site, image, canonical URL, freshness/error), provider adapters where valuable, privacy controls, collapse/hide, and dependable plain-link fallback.
- **[M10] Embeds can recurse without a cycle/depth guard.** An artifact body can embed another artifact by ID (`src/components/markdown/attachment-renderer.tsx:486-497`), and the embedded body recursively uses the same renderer (`src/components/embeds/artifact-embed.tsx:128-147`). A → B → A, or a long chain, has no visited-ID set or maximum depth. **Intent:** enforce an embed depth/budget and render a clear circular-reference card.
- **[M11] Artifact-type contracts drift across surfaces.** Prisma/tRPC include `NOTE` (`prisma/schema.prisma:485-497`, `src/server/routers/artifact.ts:65-66`); MCP artifact schemas omit it from list/create/update/promote (`src/server/services/mcp.ts:8275-8289`, `src/server/services/mcp.ts:8369-8383`, `src/server/services/mcp.ts:8419-8435`, `src/server/services/mcp.ts:8494-8507`); the detail type selector also omits NOTE (`src/app/(app)/w/[slug]/artifacts/[artifactSlug]/page.tsx:21-29`). Quick Create exposes every enum value (`src/components/quick-create.tsx:1542-1552`). **Intent:** define one shared artifact-type registry consumed by schemas, labels, icons, templates, allowed renderers, and every API/UI surface.
- **[M12] Activity events are mislabeled as issue updates.** Artifact create/update/archive/restore/delete reuse `EventKind.ISSUE_UPDATED` (`src/server/services/artifact-service.ts:157-184`, `src/server/services/artifact-service.ts:269-293`, `src/server/services/artifact-service.ts:323-341`, `src/server/routers/artifact.ts:344-365`, `src/server/routers/artifact.ts:449-466`). This makes analytics, webhooks, notification rules, and activity filtering ambiguous. **Intent:** add an artifact event family with revision, publication, visibility, attachment, review, archive, restore, and purge events.
- **[M13] Agent attribution is lost on archive through MCP.** `archiveArtifact` accepts `actorAgentId` (`src/server/services/artifact-service.ts:303-311`), but the MCP archive caller passes only `actorId` (`src/server/services/mcp.ts:8476-8481`). **Intent:** preserve human/agent actor identity consistently on every mutation and assert it in tests.
- **[M14] Artifact attachment ownership is not modeled.** `Attachment` has no uploader field (`prisma/schema.prisma:1436-1457`); deletion therefore falls back to admin-only (`src/server/routers/attachment.ts:315-330`). An ordinary artifact editor cannot remove their own mistaken upload. **Intent:** persist uploader/actor, derive delete permission from artifact role plus ownership, and retain admin override/audit.
- **[M15] The index creation overlay is not an accessible dialog.** It is a clickable fixed `<div>` without `role="dialog"`, `aria-modal`, labelled relationship, focus trap, or focus restoration; Escape is handled only while the title input owns the key event (`src/app/(app)/w/[slug]/artifacts/page.tsx:337-375`). The active/archived segmented controls also expose no selected-state semantics (`src/app/(app)/w/[slug]/artifacts/page.tsx:171-198`). **Intent:** reuse the app's modal primitive and add tab/radiogroup semantics, full keyboard navigation, focus management, error announcement, and mobile/screen-reader QA.
- **[M16] Artifact UI and authorization regression coverage is thin.** Existing artifact integration tests are strong for basic row lifecycle but do not cover concurrency, `publish:false`, accepted-state edits, archive direct reads, status/`archivedAt` divergence, attachment cleanup/audit, GUEST writes, narrowed API keys, or project-only scope (`src/server/routers/__tests__/artifact.test.ts:35-169`, `src/server/routers/__tests__/artifact-lifecycle.test.ts:33-195`). There is no artifact-list/detail Playwright flow; the only e2e artifact assertion counts recent cards in Command Center (`tests/e2e/command-center-layout.spec.ts:41-49`). **Intent:** add permission-matrix, concurrency, lifecycle-invariant, SSRF, renderer-contract, attachment-purge, version-diff/restore, and responsive/accessibility e2e suites.

## Implementation-ready enhancement backlog

### Foundation and security first

- **Central artifact authorization service** — one `canRead/canEdit/canPublish/canShare/canDelete` decision path for session users, guests, agents, API keys, public tokens, embeds, attachments, and exports.
- **Artifact-aware API-key scope** — project/initiative/issue derivation, explicit standalone-artifact policy, filtered list/search, deny-by-default reads, and regression tests for every narrowed dimension.
- **Safe URL metadata pipeline** — redirect-hop validation, DNS/IP blocking, egress policy, response caps, cache, sanitization, rate limits, and an operator kill switch.
- **Revision model v2** — immutable full-content revisions, optimistic locking, draft head, latest revision, published revision, compare, restore-as-new, immutable version URLs, and provenance per revision.
- **Lifecycle invariants** — explicit draft/review/accepted/archive/unpublish/revoke/delete/purge transitions; no dual `status`/`archivedAt` drift; approval and actor metadata.
- **Attachment integrity** — target foreign-key strategy or cleanup registry, uploader identity, artifact-role permissions, audit events, purge jobs, quota recovery, and broken-reference repair tooling.

### Authoring and versioning

- **Artifact composer** — templates by type, title/summary/body/assets in one flow, autosaved drafts, render preview, formatting shortcuts, dirty-state recovery, and changelog/reviewer controls.
- **History workspace** — version preview, author and source, changelog, inline/side-by-side diff, compare any two, restore, fork, copy version link, and raw/rendered export.
- **Publication workflow** — explicit Save revision versus Publish; accepted publication remains stable while a new draft is edited; schedule/unpublish/revoke and publication-impact preview.
- **Collaboration** — owner/editor/commenter/viewer roles, revision comments/annotations, mentions, review requests, presence where justified, and a fork/remix path that never silently mutates the source.

### Sharing and governance

- **Audience model** — private, named users/groups, workspace, authenticated link, and public link; audience and edit role are separate.
- **Share surface** — share dialog with exact audience, role, version pin/follow-latest choice, expiry/password options where policy allows, copy link, and “who can access” summary.
- **Public artifact route** — minimal unauthenticated renderer with no workspace data leakage, safe asset delivery, robots/indexing control, abuse reporting, revocation, and branded metadata.
- **Governance controls** — workspace policy for public sharing and interactive content, retention, legal/audit export, takedown, secret scanning, malware/content scanning, and durable visibility events.

### Rich rendering and assets

- **Typed renderer registry** — explicit content kind and versioned schema for Markdown, code, image/gallery, SVG, diagram, data/chart, sandboxed HTML, interactive local bundle, and hosted site/app.
- **Artifact asset manager** — upload/paste/drop, insertion at cursor, reusable asset library, image dimensions/crop/alt text, gallery reorder, replace without broken history, file preview, and per-revision asset manifest.
- **General link cards** — safe cached Open Graph metadata, provider adapters, stale/error states, preview privacy policy, collapse/hide, and plain-link fallback.
- **Sandbox tiers** — static Markdown/media by default; separately isolated HTML/SVG; CSP-constrained interactive bundles with no ambient Forge credentials; hosted apps/sites only through a deploy boundary with explicit secrets/data permissions.
- **Export and portability** — raw Markdown/source, detected code file, PDF/print, self-contained static archive where safe, and complete revision-plus-assets export.

### Discovery and workflow integration

- **Server-side artifact library** — full-text search, filters (type/status/author/project/issue/source/date/visibility), sorting, pagination, favorites/recents, saved views, and slim list DTOs.
- **Global command-palette results** — title/slug/version/source matching and direct actions such as open, copy link, duplicate, archive, or create from template.
- **Relationship graph** — artifacts on issue/project/run/goal pages; clickable source provenance; backlinks for embeds/context sets/canvases; related artifacts and broken-reference states.
- **Capture everywhere** — promote selected chat/comment/note/run/issue/file content with a review sheet; preserve source snapshot and backlink; support merge into an existing artifact as a new draft/revision.
- **Agent contract parity** — shared artifact type registry, artifact-specific scopes, create-draft/update-draft/publish/compare tools, asset tools, and precise audit attribution.

### Quality gates

- **Invariant tests** — revision ownership, publication pointers, archive state, attachment cleanup, source validity, actor attribution, and concurrency.
- **Permission matrix** — owner/admin/member/guest/agent/narrowed key/public viewer across read, embed, asset, edit, publish, share, archive, restore, and purge.
- **Renderer security suite** — scriptable URLs, HTML/SVG sandbox escape, recursive embeds, oversized content, external media privacy, CSP, clickjacking, and malicious attachment metadata.
- **Product e2e suite** — create/edit/preview/publish/share/version compare/restore/archive/revoke/delete, responsive layouts, keyboard-only use, focus management, screen-reader names/states, and empty/error/offline flows.

## Suggested delivery order

1. **Security/integrity patch:** C1-C3, attachment audit/purge, archive invariants, actor attribution, and tests.
2. **Revision/publication core:** immutable full revisions, optimistic locking, history preview/diff/restore, and explicit publish pointer.
3. **Authorization/sharing core:** artifact roles, audiences, public route, version-pinned links, policy and audit.
4. **Authoring/assets:** target-agnostic attachment manager, asset insertion, templates, autosave, preview, and exports.
5. **Rich renderer registry:** typed static formats first; sandboxed interactive content second; hosted sites/apps as a separate deploy product boundary.
6. **Discovery/integration:** global search, relationships/backlinks, capture everywhere, Command Center/library refinements, and agent-tool parity.

This order intentionally prevents a polished renderer or public-sharing feature from amplifying today’s authorization, SSRF, lifecycle, and revision-integrity gaps.
